## 一、设计问题定义

这次探索要回答 3 个问题。三个都来自现状缺口，不是凭空找的方向。

### Q1｜Gate 0 之前，主链路该继续加功能，还是先把判定可靠性测掉？

**为什么是它**：

`app/engine/judge.py` 的 `P0_已通过 = False`，`判()` 固定返回「不判定」（15·§6.2）。
这意味着 S5/S6/S7 的三种反馈里，**只有「不判定」这一支在真实运行**，另外两支（一致 / 不一致）只存在于代码和文档里（`flow.py:249`、`flow.py:255`）。

22·§二写明：Gate 0 不过，产品形态要改，**不是硬着头皮写代码**。
在 Gate 0 之前加任何依赖判定的功能（真实判定、批改、变式、诊断聚合），都是在未验证的假设上叠代码。

### Q2｜首体验被中断后，学生怎么回来？

**为什么是它**：

- 首体验是 ≤15 分钟的硬约束（11·§6·决策 1），而学生的真实场景是「做作业中途卡住」（06·一）。
- 10·§R2 明确要求「允许中途暂停并保留进度」，13·§四也写了「允许中途暂停」。
- 现状：服务端有会话 JSON（`store/session_store.py`），`GET /api/v1/sessions/{id}` 也已实现（`api/sessions.py:47`），但**前端没有恢复入口**——页面一刷新，`state.sessionId` 就丢了，学生只能从 S1 重拍。

这是主链路上的一个真实断点，而且**不依赖判定可靠性**。

### Q3｜如果 Gate 0 失败，S5/S6/S7 的形态具体长什么样？

**为什么是它**：

15·§6.2 和 22·§二 都写了「三级判定降级为引导性提问」，但只有这一句话。
没有页面、没有状态、没有话术、没有数据记录的改动清单。
等 Gate 0 真的失败再想，会来不及；这是产品形态的 Plan B，值得先写清楚。

## 三、候选方向

> 三个方向都逐条核对了 CLAUDE.md §7 四条红线，**没有方向需要废弃**。
> 成本均为「人日·估算」，单人开发、含自测。

### 方向 A｜判定先行：Gate 0 实测工程 + 判定开关

#### A-1 核心思路

先不新增用户功能，把 Gate 0 做成**可跑、可复现、可挂门禁**的实测工程：
50—100 道真实七年级应用题 → 人工标注 → `p0_judge.py` / `p0_compare.py` → 误判正例率报告；
通过后**只翻一个开关**（`P0_已通过 = True`），让现成的 S5/S6 三支反馈生效；
不通过则转入方向 C 的形态。

这不是产品功能，是**主链路下一步的决策依据**。

#### A-2 关键交互与流程

**产品侧无新页面**。三态反馈的代码已经写好（15·§6.1；`flow.py:249-257`），只是被开关挡住：

```
S5 点选
  → judge.判(备课, 输入, "S5")
      ├─ Gate 0 未通过 → 不判定 → 「你为什么这么想？」          （现状）
      ├─ 通过 · 一致   → 「对了。」+ 具体依据                    （代码已写，未启用）
      └─ 通过 · 不一致 → 线索式提问，不判「你错了」              （代码已写，未启用）
```

**实测流程**（不属于产品页面，属于验证流程）：

1. 题目准备：50—100 道真实七年级应用题（来源：教材、练习册、教师提供）。
2. 人工标注：每题的句子类型、条件三级、隐含条件集合，以及**「集合外但成立」的学生说法**。
3. 跑测：`python p0_judge.py` → `out/model_output.json`。
4. 对比：`python p0_compare.py` → 四个数字（准确率 ×2、误判正例率、说不准率）。
5. 门禁：误判正例率 = 0 才允许翻开关；否则保持「不判定」，进入方向 C。

**开关怎么翻**：`engine/judge.py` 顶部 `P0_已通过`；
文档要求「改这个值之前先看 `out/P0_摘要.json`」（`judge.py:28` 注释）。

#### A-3 数据与 API 影响

| 项 | 影响 | 依据 |
|---|---|---|
| 数据契约（18） | **不动**。P0 用的是独立标注文件，不进产品库 | 18·§四 |

| `/judge` 响应 | **语义变化**：`结果` 从恒为「不判定」变成三态之一；字段不变 | 15·§6.1 |

### 方向 B｜首体验可恢复：暂停/续跑 + 事件日志

#### B-1 核心思路

把「一次 15 分钟」做成**可中断、可回来**：

- 记录层：补 `session_events.jsonl`（18·§2.9 已定义、代码未实现）——Gate 1 需要「每步耗时 / 退出位置」。
- 恢复层：前端在本地记住 `session_id`，刷新或第二天打开时给**一行**「继续上次」，点击后按 `progress.next` 直接回到断点。
- **不是首页**：不建会话列表、不做课程入口；只在 S1 底部出现一行小号入口（13·§一「没有首页」不破）。

#### B-2 关键交互与流程

**S1 屏（唯一新增元素）**：

```
┌─────────────────────────────────┐
│ S1 · 拍照                        │
│                                 │
│ 先把这道题读一遍                  │
│ 不着急做。它觉得你能想出来。       │
│                                 │
│ [ 拍照 / 选图 ]  [ 直接粘贴题目 ]  │
│                                 │
│ 上次读到第 3 句  → 继续上次  [×]   │   ← 仅当本地有未完成会话时出现
└─────────────────────────────────┘
```

**暂停**：顶栏加一个 ghost「暂停」；点击后

- 前端停止计时、显示「先放这儿，下次接着读」；
- **不改变会话状态**（仍停在 `ANNOTATING` / `GRADING_CONDITIONS` / `PROBING_IMPLICIT`）；
- 不写卡点、不写 stuck——暂停不是失败。

**恢复**：

```
GET /api/v1/sessions/{id}
  → status = ANNOTATING
  → progress.next = {step:"S5", target_ref:"sentence:2", text:"…"}
  → 前端直接渲染 S5 屏，从第 3 句继续
```

**与 13·§五「只能向前」的关系**：暂停/恢复**不提供后退**；已提交的作答仍然不可改；恢复只是回到「当前未答的那一项」。

### 方向 C｜无判定教练：Gate 0 失败时的引导性提问形态

#### C-1 核心思路

如果 Gate 0 失败（或长期无法通过），把 S5/S6/S7 从「判对错」改成**只提问**的教练形态：

- 每个选择都换成一个追问，不出现「对了 / 不一致」；
- S8 只总结过程，不打勾、不打叉、不打分；
- **不写 `pass/fail` 卡点**，只记 `undetermined` 与 `stuck`。

这是 15·§6.2 / 22·§二 已经写下的降级预案，但还没有具体设计。**本轮只写方案，不写代码**。

#### C-2 关键交互与流程

**S5 逐句标注（引导模式）**：

```
标题：一句一句看
小字：第 2 / 5 句。先看它在这道题里干什么。
[ 句子原话 ]
[背景] [条件] [问题] [指令]
        ↓ 点选后
┌ 反馈 ────────────────────────┐
│ 你为什么觉得它是「条件」？        │
│ 这句话里有没有给数字？           │
│ [ 继续 ]                       │
└──────────────────────────────┘
```

- 保留四个选项（动作还在——「标记」是产品的核心识别度，15·§七）；
- 点选后**只出现一个追问**，不判对错；
- 「继续」推进下一句；40 秒未动 → 记 stuck，继续。

**S6 条件定级（引导模式）**：
保留三级选项，点选后只问「它是拿来就能用，还是要先转一步？」；不做判定。

**S7 隐含条件**：保留开放提问 + 「说不出来」；只记「说过 / 说不出」，不判命中。

**S8 收束（引导模式）**：

```
标题：这道题你已经读明白了。
大字：你一句一句看了 5 句，每一句都想过它在这道题里干什么。
小字：现在你可以去写了——写完拍给我看。
【可选，待议】哪一句最难？  [ 学生选一句 ] → 结束
```

**状态机不变**：S1—S8 的 12 个状态、8 条守卫完全复用（15·§四）；变化只在：
`verdict` 恒为「不判定」，反馈文案换成追问，S8 措辞换掉「标对了 N 句」。

## 四、对比与推荐

### 4.1 对比表

| 维度 | A 判定先行 | B 可恢复首体验 | C 无判定教练 |

### 4.2 推荐与排除理由

**推荐：A 先做；B 放到 Gate 1 前；C 只写预案。**

1. **A 是唯一能改变后续所有决策的一步。**
   Gate 0 通过 → S5/S6 的真实反馈成立，主链路才算验证过；
   Gate 0 不通过 → C 成为主形态，A 的结论就是 C 的触发器。
   先做 B/C 的功能，都是在未验证的判定假设上叠代码（22·§二）。

2. **C 现在只写方案、不写代码。**
   它完全依赖 Gate 0 的结果；提前实现会浪费，提前设计能避免失败时慌乱。

3. **B 是 Gate 1 的准备，不是 Gate 0 的替代。**
   它不碰判定，适合在 Gate 0 跑完后、家庭实测前做；
   现在做会撞上「没有首页」的形态问题，收益被 Gate 0 的不确定性打折。

**排除（不作为本期主方向）**：

- 「先做 S9 写解答 / S10 批改」——Gate 2 之前做批改，等于跳过红线（22·§四）。
- 「先做家长端周摘要」——v1 明确不做（11·§6·决策 6）。
- 「先做变式题」——首体验不触发（11·§6·决策 2），且依赖生成 + 审核，成本远高于本期。
